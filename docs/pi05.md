# PI0.5 training

The PI0.5 path keeps the capture dataset and the training view separate:

```text
LeRobot v3 capture (schema-declared fields/FPS/DoFs)
  -> validated episode-aware downsampling
  -> LeRobot v2.1, 15 Hz, 224x224 RGB
  -> normalization statistics
  -> schema-equivalent native LeRobot v2.1 view
  -> official isolated v2.1-to-v3 conversion
  -> OpenPI v2.1 normalization statistics
  -> LeRobot/PyTorch PI0.5 LoRA training and PEFT inference
```

## External environment

The current official OpenPI checkout was audited at commit
`15a9616a00943ada6c20a0f158e3adb39df2ccac`. It pins LeRobot to commit
`0cf864870cf29f4738d3ade893e6fd13fbd7cdb5`, whose dataset codebase version is
`v2.1`. Keep this environment separate from the lightweight SLaI runtime:

- Python 3.11 (the official project requires `>=3.11`)
- NumPy `<2.0`
- JAX CUDA 12, Torch `2.7.1`, and the official OpenPI dependency set
- the pinned LeRobot v2.1 checkout/runtime

The lightweight SLaI environment remains separate. Conversion uses
`.venv-lerobot-v3`, v2.1 writing/norm uses `third_party/openpi/.venv`, and the
available `data/models/pi05-base/model.safetensors` trains in `.venv-lerobot-v3`.
Full training forwards LeRobot's native metrics to the `slai-pi05` SwanLab project. Install the
logging dependencies into that environment with
`uv pip install --python .venv-lerobot-v3/bin/python '.[pi05-train]'`, then run `swanlab login` once.
Smoke training deliberately leaves remote logging disabled.
The safetensors checkpoint is not an OpenPI JAX/Orbax checkpoint.

The official JAX path remains available in parallel and calls OpenPI's unchanged
`scripts/train.py` through the existing schema transforms:

```bash
uv run slai-pi05 train --config configs/pi05_h100_jax.yaml --execute
```

On the H100 platform, `deploy/h100_train_jax.sh` is the foreground launcher.
Its batch size is global, while the PyTorch launcher's batch size is per GPU.

Inspect each operation before executing it:

```bash
uv run slai-pi05 convert
uv run slai-pi05 norm
uv run slai-pi05 config --execute --smoke
uv run slai-pi05 train --execute --smoke
uv run slai-mi-infer \
  --config configs/inference_pi05_round10.yaml --execute
```

For a new capture, the compact path is:

```bash
# Latest compatible committed capture; add --smoke for the one-step acceptance run.
uv run slai-pi05 all --run-id RUN_NAME --execute --smoke

# The command above prints and writes this run-specific file.
uv run slai-mi-infer --config outputs/pi05/RUN_NAME/inference.yaml --execute

# Dry-run only. Real execution also requires the standard confirmation phrase.
uv run slai-deploy-real --config outputs/pi05/RUN_NAME/inference.yaml
```

`all` reuses the existing convert, norm, config, and train stages. It selects the
latest compatible committed capture unless `--source` is supplied, keeps every
derived path under the run name, and never uploads the local dataset. Real
deployment refuses an uncommissioned task start pose and routes finite,
speed-limited actions only through the existing hardware supervisor.

Runtime paths are declared in `configs/pi05.yaml`. Input fields, camera roles,
DoF indices/masks, model slots/padding, FPS and horizon are declared once in
`configs/input_schema.yaml`. The converter refuses to overwrite an existing
target and never samples an action horizon across episode boundaries.

The current YAML selects UR-base `tcp_xyz + consecutive-column rotation6d + wujihand_actual`
for policy state (29 physical values) and `tcp_velocity + wujihand_target` for
physical action (26 values). Both are padded to the PI0.5 model's 32-value
boundary. Legacy captures containing `tcp_xyz + UR rotation-vector` are upgraded
during conversion; new captures store the first rotation-matrix column followed
by the second (`r00,r10,r20,r01,r11,r21`). Angular velocity remains a
base-frame twist and is not treated as an orientation. These dimensions and
mappings are not hard-coded in the converter. Inference splits the physical
vector back into named UR5/Wuji components before the supervisor bridge.
`convert --execute` creates the OpenPI v2.1 dataset and both native training
views in one command. The official LeRobot v2.1-to-v3 converter runs against a
temporary copy, so it cannot rename or mutate the retained native v2.1 source.
The command then computes streaming q01/q10/q50/q90/q99 statistics for the
configured training vectors; `train --execute` refuses a v3 view without q01/q99.

Round 10 evidence:

- v2.1: `data/training/pi05/block_into_box_v21_schema_round10`, 1 episode / 31 frames / 15 Hz,
  three videos, state[32], action[26]
- norm: `data/normalization/pi05_round10/slai_pi05_real_lora/local/slai-ur5-wujihand-pi05/norm_stats.json`
- smoke checkpoint: `outputs/pi05/cli-smoke-round10/checkpoints/000001`, loss 1.069,
  11.52M LoRA parameters, 9.92 GiB peak GPU memory
- inference: three image tensors `[1,3,224,224]`, state `[1,32]`, model action `[1,32]`,
  physical action `[1,26]`, 0.346 s forward time

Historical row-interleaved rotation-6D evidence (dataset
`block_into_box-20260816T194416`):

- source: LeRobot v3, 1 episode / 67 frames / 30 Hz, three H.264 videos
- converted: 1 episode / 34 frames / 15 Hz, physical state[29], action[26]
- native training view: state[32], action[32], three 224x224 AV1 videos
- one-step LoRA checkpoint:
  `outputs/pi05/block_into_box_20260816T194416_rot6d_1step/checkpoints/000001`,
  loss 1.513 and 9.92 GiB peak GPU memory

Those converted artifacts and that checkpoint predate the consecutive-column
correction and must not be used with the current schema. The configured output
paths now contain `rot6d_columns`, forcing conversion and training to create
new artifacts instead of silently reusing the incompatible interleaved data.

Project data layout:

```text
data/raw/                    # untouched source captures
data/training/pi05/          # converted LeRobot v2.1 training roots
data/normalization/pi05/     # OpenPI norm stats for those roots
```
